    01 · dim_platform_builds

    Analytics platforms, built and made better.

    Sometimes the work starts from zero. Sometimes there's already a modern stack, but the next useful thing still needs to get built. I work across ingestion, models, metrics, and interfaces to ship things people actually use.

    Timesheet automation and workforce planning at LERMA/

    PYTHON · REST APIs · METABASE · GCP · DBT
    Problem
    Several people spent real time every week pulling timesheets by hand out of Webvantage/AQUA and pasting them into messy Excel. And the allocation plans built on top of that mess could only be adjusted once a year.
    System built
    Automated API ingestion of timesheets, feeding a live Metabase dashboard self-hosted on GCP with RBAC for the CFO and 1–5 department heads. I built most of it solo. A dev on my team finished the dbt modeling, which is how a team is supposed to work.
    Impact
    Agency-wide time logging for workforce planning. The CFO and I added quarterly metrics that line up logged hours against planned hours, which replaced a once-a-year spreadsheet exercise everybody dreaded.

    Paid media modeling: dbt + BigQuery

    DBT · BIGQUERY · FIVETRAN
    Problem
    Paid media data was split across platforms, and every platform had its own idea of what a conversion was and what spend meant. Ask three platforms, get three answers.
    System built
    dbt models in BigQuery with explicit day-platform-campaign grain, platform staging, and governed metric marts.
    Impact
    Executive reporting got standardized, and adding a new channel stopped breaking everything downstream of it.
    View Data Model ↗

    ProductDW: a mini ELT system

    PYTHON · SQL · STREAMLIT
    Problem
    Raw GA4 event data is not analytics-ready. It just isn't. Product KPI reporting needed more than querying raw events and hoping for the best.
    System built
    Python-orchestrated BigQuery pipeline with staging, core, and mart tables plus a Streamlit consumption layer.
    Impact
    Turned raw events into reusable product analytics tables and a practical KPI interface.
    GitHub ↗

    API feed to BigQuery

    PYTHON · REST APIS · CLOUD RUN
    Problem
    Event data needed to get into the warehouse reliably. Manual exports are how you end up with duplicate loads and numbers nobody trusts.
    System built
    Python ingestion job deployed on Cloud Run with API auth, pagination, schema mapping, and BigQuery watermarking.
    Impact
    A scheduled, low-maintenance pipeline feeding the warehouse for downstream reporting.

    03 · dim_governance

    Governed metrics are the trust layer.

    If the model is messy, everything downstream is harder than it should be.

    I keep models boring on purpose. Clear grain, consistent naming, and logic defined once instead of copied into twelve places. Definitions belong in governed models, not scattered across dashboard calculations where nobody can find them. Because the minute two dashboards show two different numbers, the meeting stops being about the business and starts being about whose number is right. Nobody wins that meeting.

    Raw→ Staging→ Intermediate→ Mart→ BI

    BeforeExcel reporting: manual refreshes, version drift, hidden logic.

    AfterAutomated BI: scheduled pipelines, governed metrics, shared definitions.

    BeforeSSRS extracts: static outputs that need an analyst to touch them.

    AfterLooker workflows: reusable models, self-serve paths, decision dashboards.

    BeforeSiloed metrics: teams debate definitions instead of outcomes.

    AfterUnified layer: shared marts and canonical measures across teams.

    04 · dim_partnership

    Dashboards are products. Stakeholders are customers.

    I learned this one the hard way. Early in my career I built dashboards I was proud of that nobody opened. A dashboard is not useful just because it exists. If people don't use it in their actual workflow, it's dead, no matter how clean the SQL is. So now I think about whether people will actually use it before I build it. And sometimes the right product isn't a dashboard at all.

    Lite CRM for the CGO at LERMA/

    SUPABASE POSTGRES · AUTHENTIK · OUTLOOK SYNC
    Problem
    The CGO's leads and growth pipeline lived in an Excel doc. No shared view of 50+ historical and current leads and opportunities, and nothing he could check on the go.
    System built
    A lightweight browser CRM on Supabase Postgres with auth via Authentik, Outlook email sync, and a mobile-friendly view for leads and notes on the go. Built solo.
    Impact
    The CGO uses it regularly for growth updates and pipeline management. A spreadsheet nobody wanted to open became a product somebody uses every day.

    PRINCIPLES

    How the work holds together.

    Start with the decision

    If it's not tied to a decision, it's probably not the right problem yet.

    Make grain explicit

    Every model should say what one row means. This prevents hidden joins and metric drift.

    Centralize metric logic

    Definitions belong in governed models, not scattered across dashboard calculations.

    Design for adoption

    A dashboard is successful when stakeholders return to it during real operating rhythms.

    Reduce analyst drag

    Good systems remove repeated pulls, one-off reconciliations, and preventable explanations.

    Keep builders close to users

    The person modeling the data should understand the workflow the dashboard supports.
